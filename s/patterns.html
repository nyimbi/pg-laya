Query patterns

How to turn a request into SQL: (1) decide the output shape → function, (2) write every cheap condition in SQL first, (3) phrase the model's condition literally, (4) call it on a base table or view, (5) if the user has not chosen a threshold, start with laya_prob() and look. Cost: ~175 input tokens per row.

1. Filter (yes/no)

sql
SELECT id, subject
FROM tickets
WHERE status = 'open'                              -- cheap, indexed, runs first
  AND created_at >= now() - interval '7 days'
  AND laya(tickets, 'the customer threatens to cancel or asks for a refund');

Stricter cut: laya(tickets, '…', 0.8). Negation: NOT laya(tickets, '…') keeps rows below the threshold, including ambiguous ones; for "clearly not X" use laya_prob(...) < 0.2.

2. Rank / top-N

sql
SELECT subject, laya_prob(tickets, 'the customer is angry') AS p
FROM tickets
WHERE status = 'open'
ORDER BY p DESC
LIMIT 20;

LIMIT does not save API calls here (sorting needs every probability), but a WHERE laya(...) + LIMIT without ORDER BY stops the read-ahead after the in-flight window.

3. Pick a threshold from the distribution

sql
SELECT width_bucket(laya_prob(reviews, 'the customer sounds frustrated'), 0, 1, 10) AS bucket, count(*)
FROM reviews
GROUP BY 1 ORDER BY 1;

Then SELECT … WHERE laya(reviews, '…', 0.7). The second statement is free: same table + condition → cache. Spot-check the middle with WHERE laya_prob(...) BETWEEN 0.4 AND 0.6 to see what the model finds ambiguous.

4. Classify into a closed set

sql
SELECT laya_choice(tickets, 'which team should handle this ticket?',
                   ARRAY['billing', 'technical', 'security', 'sales']) AS team,
       count(*)
FROM tickets
WHERE status = 'open'
GROUP BY 1
ORDER BY 2 DESC;

Write the options as a person would read them; every row must fit one. Persisting labels:

sql
UPDATE tickets t
SET team = laya_choice(t, 'which team should handle this ticket?',
                       ARRAY['billing','technical','security','sales'])
WHERE team IS NULL;

5. Score on a rubric

sql
SELECT name,
       laya_score(products, 'how luxurious is this product?',
                 ARRAY['budget', 'mid-range', 'premium', 'luxury']) AS luxury   -- 0..3
FROM products
ORDER BY luxury DESC;

-- combine rubrics (0..1 each):
SELECT name,
       0.6 * laya_score_norm(p, 'how luxurious?', ARRAY['budget','mid-range','premium','luxury'])
     + 0.4 * laya_score_norm(p, 'how urgent is restocking?', ARRAY['not at all','somewhat','very']) AS priority
FROM products p
ORDER BY priority DESC;

6. Limit what the model sees: a view

The whole row is sent. When the table has columns the model does not need (PII, large blobs, internal ids), make a view — views are streamed and batched like tables.

sql
CREATE VIEW ticket_text AS
SELECT id, subject, body FROM tickets WHERE status = 'open';

SELECT id FROM ticket_text v WHERE laya(v, 'the customer threatens legal action');

7. Joins

laya() takes one row type, so judge the side that carries the text and join the rest. To judge a combination of columns from two tables, build a view over the join.

sql
SELECT c.name, t.subject
FROM tickets t
JOIN customers c ON c.id = t.customer_id
WHERE c.plan = 'enterprise'
  AND laya(t, 'this is a billing dispute');

8. Aggregates and CASE

sql
SELECT date_trunc('week', created_at) AS week,
       count(*) FILTER (WHERE laya(reviews, 'the customer sounds frustrated')) AS frustrated,
       count(*) AS total
FROM reviews
WHERE created_at >= now() - interval '90 days'
GROUP BY 1 ORDER BY 1;

Two different conditions are two scans (two cache keys). Prefer one laya_choice with both options when they are mutually exclusive.

9. Large tables and spend

Every row reaching laya() costs tokens. In order of preference:

  1. Indexed predicates before laya() (status, dates, ids, tsvector @@ for keywords).
  2. A view with only the needed columns (fewer characters per row).
  3. A spend guard while exploring: SET laya.max_rows_per_statement = 2000;
  4. LIMIT with a plain WHERE laya(...) (stops early).
  5. Sample first to test the wording: FROM reviews TABLESAMPLE SYSTEM (5) WHERE laya(reviews, '…').

Estimate before running: rows × ~175 tokens × $0.042 / 1M. 10,000 rows ≈ 1.75M tokens ≈ $0.07.

10. Same session, repeated exploration

Answers are cached per (relation type, question, kind, options) and row content for the backend session. Iterating on thresholds, sorting, LIMIT, joins or aggregates over the same condition is free; changing a single word of the condition is a new scan. Keep the session open while exploring; SELECT laya_stats() shows cache_hits climbing.

Wording checklist for the condition

  • Name the observable behaviour, not the label: 'the reviewer says the product broke within a month' rather than 'quality issue'.
  • One condition per call. "A or B" is fine when the user wants either; a list of five things is better as laya_choice.
  • Refer to the row as "the record", "the ticket", "the customer" — matching the column names the model will see.
  • Do not ask for computation ('the total is above 100'): put it in SQL.
  • Language: the condition can be in one language, the data in another. Say which language a text column is in if it matters.
