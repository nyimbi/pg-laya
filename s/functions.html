pg-laya docs
Local, plain-language predicates for PostgreSQL

Functions

All functions take the row as first argument: the table, view or subquery alias (laya(people, …), laya(p, …) after FROM people p). Postgres passes the whole row as a composite value; the extension serialises it with to_json. Column names are part of what the model sees, so descriptive names help. All are STABLE.

Judgment functions

laya(row, condition [, threshold]) → boolean

The predicate. Equivalent to laya_prob(row, condition) >= coalesce(threshold, laya.threshold, 0.5). The threshold argument beats the laya.threshold GUC beats 0.5.

sql
SELECT * FROM reviews WHERE laya(reviews, 'the customer sounds frustrated');
SELECT * FROM reviews WHERE laya(reviews, 'the customer sounds frustrated', 0.8);

laya_prob(row, condition) → float8

Probability 0..1 that the row satisfies the condition. Use for ranking, distributions and choosing a threshold. Calibrated: ambiguous rows sit near 0.5.

sql
SELECT subject, laya_prob(tickets, 'the customer is angry') AS p
FROM tickets ORDER BY p DESC LIMIT 20;

laya_choice(row, question, options text[]) → text

The most likely option, returned verbatim from options. Options are a closed set — there is no "none of the above" unless you add one, so prefer a set where every row has a sensible answer.

sql
SELECT laya_choice(tickets, 'which team should handle this?',
                   ARRAY['billing','technical','security','sales']) AS team,
       count(*)
FROM tickets GROUP BY 1;

laya_score(row, question, levels text[]) → float8

Probability-weighted position on the ordered levels, from 0 (first) to n-1 (last). A row the model puts at 60% premium / 40% luxury on ['budget','mid-range','premium','luxury'] scores 2.4. List levels low → high.

laya_score_norm(row, question, levels text[]) → float8

laya_score / (n-1), i.e. 0..1, so scores on rubrics of different lengths are comparable.

laya_confidence(row, question, kind, options text[]) → float8

Confidence 0..1 of a 'choice' or 'score' answer. Route low-confidence rows to a human:

sql
SELECT id,
       laya_choice(t, 'which team?', ARRAY['billing','technical','sales']) AS team,
       laya_confidence(t, 'which team?', 'choice', ARRAY['billing','technical','sales']) AS conf
FROM tickets t
WHERE laya_confidence(t, 'which team?', 'choice', ARRAY['billing','technical','sales']) < 0.6;
✓

The same (question, kind, options) triple hits the same cache entry, so calling laya_choice and laya_confidence with identical arguments costs one API call, not two.

laya_eval(row, question, kind DEFAULT 'noul', options text[]) → jsonb

The raw answer. kind is 'noul', 'choice' or 'score'; options is required for the last two. Use it when you need the full probability vector (e.g. multi-label routing).

kindjsonb shape
noul{"type":"noul","noul":0.93}
choice{"type":"choice","choice":"billing","probabilities":{"billing":0.8,"technical":0.15,"sales":0.05},"confidence":0.8}
score{"type":"score","score":2.4,"legend":{...},"probabilities":{...},"confidence":0.6}

Session helpers

laya_stats() → jsonb

Counters for the current backend session: requests, input_tokens, output_tokens, rows_evaluated, cache_hits, api_ms, batches, errors, retries, estimated_cost_usd, cached_answers, in_flight, connections. estimated_cost_usd = input_tokens × $0.042 / 1M (output tokens free).

laya_cache_clear() → void

Forgets cached answers and read-ahead state for this session only. Answers are cached by row content, so an UPDATE changes the hash and re-judges automatically. Mostly needed when switching laya.model and wanting fresh answers.

laya_version() → text

Extension version, e.g. 0.3.0. Compare with SELECT default_version FROM pg_available_extensions WHERE name='laya' to see whether ALTER EXTENSION laya UPDATE is pending.

⚠

_laya_eval(…) is the internal function every wrapper calls. Its signature is not part of the stable API — do not call it directly in user-facing SQL.
